# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Course project: a FastAPI service that receives a meeting transcription and returns a software estimation generated by an LLM, using a **CAG** (Cache-Augmented Generation) architecture. Static example estimations are injected directly into the system prompt as few-shot context. There is no retrieval, no database and no persistence.

**Follow the folder layout and file names below exactly.** The teaching assistant checks against them. User-facing docs (README.md) are in Spanish; code, comments and specs are in English.

## Workflow

- Work is planned and implemented with **OpenSpec** (`openspec/`, project context in `openspec/config.yaml`), with **one change per exercise step** (see below).
- The user makes every commit manually. Never commit or push. Propose each commit message (Conventional Commits, English subject, body listing what it delivers) together with the explicit list of paths to `git add`.
- Each change follows this cycle. **Stop at every review point** and wait for the user before continuing:
  1. `/opsx:propose`: create `proposal.md`, `design.md`, `specs/**/spec.md` and `tasks.md`. Then stop. The user reviews them.
  2. After the user approves the artifacts, propose a commit message for them (e.g. `docs(openspec): propose <change-name>`).
  3. `/opsx:apply`: implement the tasks. Then stop. The user reviews and verifies the code.
  4. After the user approves the code, propose a commit message for the implementation (e.g. `feat: ... (paso N)`).
  5. `/opsx:sync` then `/opsx:archive`: update the main specs in `openspec/specs/` and move the change to `openspec/changes/archive/`. Then propose a commit message for that (e.g. `docs(openspec): archive <change-name>`).
- Every OpenSpec markdown file starts with a level-1 title named after the file, without `.md`: `# Proposal`, `# Design`, `# Spec`, `# Tasks`. The user's VS Code markdown linter requires it. This is also enforced through `rules:` in `openspec/config.yaml`.
- Branch: `feature/sesion-02`, to be pushed to GitHub and delivered to the teaching assistant.
- `_docs/` (gitignored) holds the user's local course notes: the exercise brief (`_docs/brief.md`, in Spanish) and a prompt log. Read the brief for context on each step. Tracked files must not link to anything inside it.

## Commands

```bash
uv sync                                   # install deps from uv.lock into .venv
uv add <pkg>                              # add a dependency (then re-export requirements.txt, below)
uv run uvicorn app.main:app --reload      # run the API, http://localhost:8000 (Swagger at /docs)
uv export --no-hashes --no-emit-project --no-dev --format requirements-txt -o requirements.txt
```

`pyproject.toml` + `uv.lock` are the source of truth. `requirements.txt` is generated from the lock for pip users (`pip install -r requirements.txt`): never edit it by hand. The project has no build backend. `app` is imported from the repo root, so run commands from there.

No tests, linter or CI exist yet (see step 8).

## Target architecture

```text
app/
  __init__.py
  main.py                 FastAPI app: title/description, GET /health, includes estimations router with prefix /api/v1
  config.py               pydantic-settings Settings loaded from .env (see step 2 for the variables)
  routers/__init__.py
  routers/estimations.py  POST /api/v1/estimate; Pydantic request {transcription} / response {estimation, model, provider, ...}
  services/__init__.py
  services/llm_service.py builds messages, calls the LLM, returns the estimation
  context/__init__.py
  context/examples.py     ESTIMATION_EXAMPLES: list of {meeting_summary, estimation} (>= 2, fictitious)
transcripciones/          sample request bodies {"transcription": ...} for curl -d @file (extra, not in the course layout)
.env                      real values, gitignored
.env.example              same variables, empty values, committed
.gitignore
pyproject.toml
README.md
```

Request flow: router → `llm_service` → messages `[system]` (expert software estimator role + every `ESTIMATION_EXAMPLES` entry) and `[user]` (the transcription) → LLM → `[assistant]` estimation → JSON response.

- Providers: **Anthropic (`claude-haiku-4-5`) is the default and the first one implemented**, because the user only has an Anthropic API key for now. `claude-haiku-5-5` is supported as an opt-in alternative (`LLM_MODEL=claude-haiku-5-5`): it is cheaper, has thinking on by default, and the service sends it `effort: low`. OpenAI (`gpt-4o-mini`, `LLM_PROVIDER=openai`) is implemented and verified live. `gpt-4o-mini` is deprecated by OpenAI but stays the default as the course model; `gpt-6-luna` is supported as an opt-in alternative (`LLM_MODEL=gpt-6-luna`, sent with `reasoning_effort: low`). Per-model request options live in `MODEL_REQUEST_OPTIONS`, and an `LLM_MODEL` from the other provider is rejected at startup. Providers are registered in `PROVIDERS` in `app/services/llm_service.py`; Gemini may be added later the same way.
- Secrets: API keys only come from `.env` via `config.py`, never in code.

## Exercise steps (one OpenSpec change each, committed per the Workflow cycle)

1. **Init project**: uv project, dependencies (`fastapi`, `uvicorn[standard]`, `pydantic-settings`, `openai` and/or `anthropic`, `python-dotenv`), full folder skeleton above.
2. **Config**: `config.py` with Pydantic `BaseSettings` reading `.env`; `.env.example` with the variables and empty values; `.env` with real values and listed in `.gitignore`. Variables:

   | Variable            | Description                       | Default                                                                      |
   | ------------------- | --------------------------------- | ---------------------------------------------------------------------------- |
   | `OPENAI_API_KEY`    | OpenAI API key                    | none (required if OpenAI is used)                                            |
   | `ANTHROPIC_API_KEY` | Anthropic API key                 | none (required if Anthropic is used)                                         |
   | `LLM_PROVIDER`      | Provider: `openai` or `anthropic` | `anthropic` (course default: `openai`)                                       |
   | `LLM_MODEL`         | Model to use                      | provider's economy model, `claude-haiku-4-5` (course default: `gpt-4o-mini`) |
   | `APP_ENV`           | Runtime environment               | `development`                                                                |
   | `LOG_LEVEL`         | Logging level                     | `DEBUG`                                                                      |

3. **Static context**: `ESTIMATION_EXAMPLES` in `context/examples.py`, at least 2 entries, each with `meeting_summary` (what the client asked for) and `estimation` (Markdown: task breakdown with hours/costs, total, team, duration).
4. **LLM service**: `services/llm_service.py` builds the system prompt + injected examples, sends the transcription as the user message, and returns the model output.
5. **Endpoint**: `POST /api/v1/estimate` in `routers/estimations.py` with Pydantic request/response schemas. Extra response fields are allowed (tokens, cost, timestamp).
6. **FastAPI app**: `main.py` includes the router with prefix `/api/v1`, adds `GET /health`, and sets title/description for Swagger. Replaces the current hello-world scaffold.
7. **Verification**: the checklist below plus the sample curl in README.md.
8. **Automation and delivery extras**: a CI pipeline (GitHub Actions) that validates the folder structure and that the service works; a meeting transcription file in the repo used as the exercise input.

Verification checklist: the server starts with `uv run uvicorn app.main:app --reload`; keys load from `.env` and never appear in code; `GET /health` returns 200; `POST /api/v1/estimate` returns an estimation that draws on the injected examples; Swagger at `/docs`; `.env` is gitignored.
